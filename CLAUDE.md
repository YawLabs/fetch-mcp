# fetch-mcp — Claude Code instructions

This is the `@yawlabs/fetch-mcp` server. Stdio MCP server. HTTP fetch with SSRF protection, HTML-to-markdown, reader-mode, metadata / link / sitemap / RSS-Atom extraction, robots.txt awareness. Node ≥22.19 (undici 8's floor; enforced by the launcher, see #16), ESM, TypeScript, tsup, vitest, biome.

## Layout

- `bin/fetch-mcp.mjs` — the npm `bin`. Runtime launcher: prefers the newest oam at or above `OAM_MIN` (0.18.0, the latest oam release), falls back to Node. Imports `dist/index.js` in-process, spawns `oam [--permission --allow-net --allow-env=FETCH_MCP_ALLOW_PRIVATE_HOSTS] run <entry> -- <argv>`, or — from an oam host below the floor, or under `FETCH_MCP_RUNTIME=node` on any oam host — hands off to `node <entry> <argv>` with piped stdio. It never serves on an oam below the floor.
- `src/index.ts` — CLI entrypoint: handles `version` / `--version`, rejects any other argument, otherwise calls `startServer()`.
- `src/server.ts` — MCP server factory, registers tool modules.
- `src/security.ts` — SSRF block list + URL validator. Security-critical.
- `src/policy.ts` — operator policy: the `FETCH_MCP_ALLOW_PRIVATE_HOSTS` parser, its stderr warning, and the gate's messages. Security-critical.
- `src/http.ts` — core request client: redirects, retries, size cap, auth, timeouts, cancellation. `createRequester(policy)` binds one server's operator policy; tools only ever call the requester they are handed.
- `src/format.ts` — `formatJson` / `formatError` helpers for MCP `content` arrays.
- `src/markdown.ts` — `htmlToMarkdown()`: the only HTML-to-markdown path. Bounded incremental domino parse, depth refusal, vendored Turndown. Security-critical (Launch-critical #22).
- `src/vendor/turndown/` — Turndown 7.2.4 (MIT), vendored with eleven patches, (a)-(k), listed in its header; excluded from biome. `src/vendor/domino.d.ts` types the domino surface `markdown.ts` uses.
- `src/tools/http.ts` — 7 HTTP method tools.
- `src/tools/content.ts` — `fetch_html_to_markdown`, `fetch_html_to_text`.
- `src/tools/reader.ts` — `fetch_reader` — main-content isolation + markdown.
- `src/tools/meta.ts` — `fetch_meta` — head metadata: OG, Twitter, JSON-LD, canonical, feeds, icons.
- `src/tools/links.ts` — `fetch_links` — absolute URL extraction with `<base>` support.
- `src/tools/sitemap.ts` — `fetch_sitemap` — XML sitemap parsing + sitemap-index chaining + gzip.
- `src/tools/feed.ts` — `fetch_feed` — RSS 2.0 + Atom 1.0 parser via fast-xml-parser.
- `src/tools/robots.ts` — `fetch_robots` + `parseRobots` + `isAllowed`.
- `src/tests/` — vitest suites. `http.test.ts` binds a real loopback server (no mocks).

## Launch-critical things you must not break

1. **SSRF defaults.** `validateUrl()` rejects private IPs, loopback, link-local, cloud metadata, CGNAT, non-`http(s)` schemes, and `localhost*` by default. Tests in `src/tests/security.test.ts` + `src/tests/http.test.ts` pin this. A regression here is a P0.
2. **Per-hop redirect re-validation.** `sendHop()` in `src/http.ts` MUST run `validateUrl()` on every URL it dials (scheme allow-list, literal-IP block list, `localhost*`) AND resolve DNS + re-run `checkIpAddress()` for every hostname `Location` it follows. Dropping the DNS step re-enables the classic DNS-rebinding → SSRF attack; dropping the `validateUrl()` step re-opens the 0.7.0-and-earlier bug where a public URL that 302'd to `http://169.254.169.254/...` (or any literal blocked IP, or `ftp://`) was fetched with the guard on -- the initial-URL check in `httpRequest()` never sees redirect targets. `src/tests/http.redirect-ssrf.test.ts` pins this; 30 of its original 35 redirect cases fail without the per-hop `validateUrl()`.
3. **Response size cap is streaming.** `httpRequest()` reads the body as a stream and aborts with an `AbortController` when `max_bytes` is hit. Don't buffer the full body and then truncate — that defeats the cap. Upper-bound `ABSOLUTE_MAX_BYTES` is 100 MiB; callers can request less, not more.
4. **JSON auto-parse only on matching Content-Type.** The client only sets `response.json` when `content-type` starts with `application/json` (or `+json`). Don't probe-parse arbitrary bodies — an XSS-laced HTML page containing a JSON fragment shouldn't end up in `.json`. Even then, `jsonAutoParseAllowed()` skips `JSON.parse` (synchronous, uninterruptible) on a body over 16 MiB (`MAX_JSON_AUTOPARSE_CHARS`), nested deeper than 1,000 levels, or opening more than 1,000,000 arrays/objects; `json` stays undefined and the raw, display-capped text is shown (`http.json.test.ts`).
5. **Default `User-Agent` includes the repo URL.** Required by common anti-bot gatekeepers to know who to contact. If you ever rename the package, update `defaultUserAgent()` accordingly.
6. **Sitemap gzip detection is on the raw bytes, not Content-Encoding.** Many sitemaps are served as `.xml.gz` with `application/x-gzip` and no `Content-Encoding`, so node fetch does not decompress. `decodeSitemapPayload()` sniffs the gzip magic (`1f 8b`) on the raw buffer; don't switch sitemap to `decodeText: true` or gzip detection breaks.
7. **JSON-LD parsing is best-effort.** `parseHtmlMeta()` swallows JSON.parse errors on malformed `<script type="application/ld+json">` blocks rather than failing the entire meta request — sites frequently ship invalid JSON-LD.
8. **Atom link picking prefers `rel="alternate"` over `rel="self"`.** The self link points to the feed XML itself, not the article — see `extractAtomLink()` in `src/tools/feed.ts`.
9. **Argument handling in `src/index.ts` runs before `startServer()`.** `version` / `--version` prints the version and exits 0 (the release smoke test depends on it); any other argument prints `Unknown subcommand` plus usage to **stderr** and exits 1; only a launch with no argument starts the server. `startServer()` binds stdio and blocks on stdin, so an argument that reaches it looks like a hang (#33). Never write diagnostics to stdout — it is the MCP channel. Every `bin/fetch-mcp.mjs` path (in-process under Node or a host oam, the spawned `oam run <entry> -- …`, or the Node handoff `node <entry> …`) reaches `src/index.ts` with no argument when the launcher itself got none; `src/tests/version.test.ts` pins all three outcomes.
10. **The `FETCH_MCP_SANDBOX` and `FETCH_MCP_RUNTIME` parsers are security-sensitive.** `parseSandboxSetting` reads `1`/`true`/`yes`/`on` (trimmed, case-insensitive) as on, `0`/`false`/`no`/`off`/unset as off, anything else as off AND named on stderr -- a security opt-in that fails OPEN on `true` or a trailing space, with nothing on stderr, is the silent downgrade this launcher promises never to make. `parseRuntimeSetting` reads `auto`/`oam`/`node` (trimmed, case-insensitive), anything else as `auto` AND named on stderr -- the same class of downgrade would let the fail-closed pairing (sandbox on + `RUNTIME=oam`) fall open on `"oam "`. The unit tests in `src/tests/launcher.test.ts` pin every accepted spelling; the integration tests pin that unrecognised values produce the on-stderr line and never serve with the wrong setting.
11. **The "runs WITHOUT `--permission`" note is printed ONLY once a serving path is committed to.** `noteSandboxNotApplied()` returns early when there is no sandbox; it is called by `fallBack` (after `fallbackInProcess` decides) and by `handOffToNode` (after `findNodeOnPath()` succeeds). A fatal exit (no Node on PATH, `RUNTIME=oam` with nothing to spawn) must never claim the server runs without the sandbox -- the line would sit above an exit that served nothing. `src/tests/launcher.test.ts` pins both sides: the line fires when the path serves, and never fires above a fatal exit.
12. **`hostOamCandidate()` puts the running process's own `process.execPath` first in discovery**, gated on its `--version` agreeing with `process.versions.oam`. A host whose oam is bundled inside the app (Yaw MCP) is the most common reason to reach discovery at all -- the sandbox needs a fresh oam, and the host's binary is the one guaranteed to exist. The version-agreement check keeps a wrapper, a `shim`, or a Node posing as oam (the suite's own preload) from masquerading as one. The integration test "spawns a fresh copy of the host's OWN oam for the sandbox when nothing else is installed" covers the new path, and "does not mistake a host whose binary reports a different version for its own oam" covers the guard.
13. **`allow_private_hosts` is gated by the operator, in `httpRequest()`, per server.** The model chooses tool arguments, so the per-call flag alone must never widen reach: `httpRequest(opts, policy)` refuses `allowPrivateHosts` unless `policy.allowPrivateHosts` is true, and the default policy refuses. `createFetchServer({ allowPrivateHosts })` binds its own frozen policy with `createRequester()` and passes that requester to every `register*Tools(server, request)`; only `startServer()` derives the value, from `FETCH_MCP_ALLOW_PRIVATE_HOSTS` (parsed like `FETCH_MCP_SANDBOX`, fail-closed, unrecognised values named on stderr). Never put the policy back in module state -- 0.7.1 did, and the most recent `createFetchServer()` then decided for every server in the process. Keep the check in `httpRequest()` -- the single path to the network -- and never let a tool import `httpRequest` directly. `src/tests/policy.test.ts` (including the two-servers case) and the operator-gate block in `http.redirect-ssrf.test.ts` pin it; suites that reach a loopback fixture opt in explicitly.
14. **`fetch` and the pinned `Agent` come from the same `undici` import.** Never switch `sendHop()` back to the runtime's global `fetch`: Node's bundled undici (6.x on 22, 7.x on 24) drives dispatchers through the legacy handler API and undici 8's `Agent` rejects it, so every guarded hostname request fails with `fetch failed` on plain Node (0.4.0-0.7.0 shipped that way; Node 20 could not load undici 8 at all). `src/tests/http.pinned-dispatch.test.ts` is a real-socket test that catches it; the mock-based suites mock `undici`'s `fetch` and cannot.
15. **The sandbox's `--allow-env` grant must list every env var `src/` reads.** Under oam `--permission` an ungranted variable is ABSENT, not an error. Today that is exactly `FETCH_MCP_ALLOW_PRIVATE_HOSTS` (`sandboxFlags()` in `bin/fetch-mcp.mjs`, pinned by the launcher test); add any new `process.env` read under `src/` there too, or it silently reads as unset under the sandbox.
16. **The launcher refuses to serve on a Node below `NODE_MIN` (22.19.0) -- on every serve-on-Node path, before any sandbox note.** undici 8's floor is 22.19.0; below it Node 20 dies at import and Node 22 < 22.15 dies mid-session on the first `content-encoding: zstd` response (no `zlib.createZstdDecompress`). `refuseOldNodeInProcess()` guards the in-process and fallback paths, `handOffToNode()` probes the found `node --version`, and `fallbackSuffix()` drops "; using Node instead" when the refusal is coming. Keep `NODE_MIN` and `package.json` `engines.node` in step; `launcher.test.ts` pins both, and fakes `process.versions.node` to drive the refusal.
17. **The sitemap gzip cap is counted by hand on a streaming gunzip, never via zlib's `maxOutputLength`.** Streaming zlib has no `maxOutputLength` cap on Node or on oam -- only the one-shot functions enforce it, and on oam only since 0.17.0 (before that a `maxOutputLength`-only cap was no cap under the launcher's preferred runtime: a 200 KB `.xml.gz` OOM-killed the server at 4 GB). The stream is what lets `signal` and the cap land between slices. `gunzipCapped()` feeds 1 KiB input slices and destroys the stream once the output count passes the cap; the slice size bounds the overshoot on oam (~1 MiB), where each written slice inflates into one chunk. The cap is the smaller of `max_bytes` and the XML parse limit: fast-xml-parser is synchronous and uninterruptible (a 19 MiB urlset stalled the server 4.65 s through 0.8.3), so `fetch_sitemap` and `fetch_feed` refuse a document past 16 MiB (`MAX_XML_PARSE_BYTES` / `MAX_FEED_PARSE_BYTES`; a 50,000-URL sitemap is ~10.6 MiB) or holding more than 1,500,000 / 1,000,000 `<` (`MAX_XML_PARSE_TAGS` / `MAX_FEED_PARSE_TAGS`: markup costs per tag, and 16 MiB of `<a/>` parsed in 6-7.5 s) before parsing -- ~3 s worst-case parse -- re-check the budget/signal right before each parse, and keep attributes ignored (sitemap) or allow-listed (feed) -- many distinct attribute names are the parser's slowest shape. Pinned in `sitemap.test.ts`, `sitemap.integration.test.ts`, `feed.test.ts`. The same rule holds for robots.txt: `robotsPathMatches()` in `src/tools/robots.ts` matches attacker-chosen `Allow`/`Disallow` patterns with a linear wildcard matcher, never a RegExp (one long `*` rule threw "regular expression too large"; twenty `/*-*-...-X$` rules backtracked ~12 s), and its line-terminator scan stays a native regex, since a charCode loop ran once per rule over the path; `robots.test.ts` pins it against the old RegExp semantics.
18. **`timeout_ms` bounds a whole attempt, DNS included, and cancellation reaches every wait.** `httpRequest()` computes one deadline per attempt (capped by `ABSOLUTE_MAX_TOTAL_MS`, 5 minutes for the whole call) and hands it to every `sendHop()` of that attempt. `sendHop()` arms its abort timer BEFORE `resolveAndPin()` and races the lookup against it (`raceAbort`) -- `dns.lookup` cannot be cancelled, and running it before the timer let a silent resolver add its full OS timeout to every hop. The caller's `signal` (tools pass the MCP request's `extra.signal`) aborts the hop in flight, the Retry-After wait (`sleepUnlessAborted`) and every later attempt. A retry starts only if its wait plus a full `timeout_ms` fit under the ceiling. `sendHop()`'s `finally` must `destroy()` the pinned Agent, never `close()` it: `close()` waits out undici's 10 s connect timeout after an abort mid-connect; the Agent's connect `timeout` is the attempt's remaining budget. `fetch_sitemap` has its own whole-call budget (`registerSitemapTools(server, request, { totalMs })`, default `ABSOLUTE_MAX_TOTAL_MS`). Pinned by `http.deadline.test.ts` (attempt budget, DNS, cancellation for all 15 tools), `http.ceiling.test.ts` (fake clock: fresh budget per retry, the retry rule, the ceiling), `http.pinned-dispatch.test.ts` (real-socket stalled TLS handshake) and `sitemap.integration.test.ts` (the sitemap budget).
19. **A DNS refusal never names the resolved address.** `resolveAndPin()`'s message goes back to the model; `DNS: jenkins.corp -> 10.20.30.40` turned every refusal into an internal host-to-IP oracle (through 0.7.1). The literal-IP refusals may echo the literal -- the caller or the redirecting server supplied it. `http.dns-rebind.test.ts` asserts the IP is absent.
20. **IPv6 is an allow-list after the named rules.** `checkIpAddress()` decides the embedding forms (mapped, SIIT, IPv4-compatible, 6to4) first, then refuses anything outside global unicast `2000::/3`, then the non-global blocks inside it (`3fff::/20`, `2001:2::/48`, `2001:10::/28`). Keep new named rules ABOVE the allow-list, and keep the embedding forms above it too, or a public embedded IPv4 (`::ffff:8.8.8.8`) starts being refused.
21. **`src/tests/oam.integration.test.ts` runs the built server on a real oam, sandboxed.** Opt-in via `FETCH_MCP_TEST_OAM=<oam binary>` (skipped otherwise). Run it before a release when oam or anything runtime-sensitive (zlib, fetch, AbortSignal, the launcher's env grant) changed -- a Node-only suite is how a `maxOutputLength` cap that oam before 0.17.0 ignored shipped. `release.sh` runs it after the build when it finds an oam at or above `OAM_MIN` (`FETCH_MCP_TEST_OAM`, else discovery), and warns instead when none is found. Oam divergence it documents but does not assert: an aborted `fetch` left its socket open on oam 0.16.3 and 0.17.0; measured closed within ~50ms of the cancel on 0.18.0, the floor.
22. **HTML-to-markdown goes only through `htmlToMarkdown()` in `src/markdown.ts`, and that path is bounded.** The page is attacker-chosen; through 0.8.3 the npm `turndown` package parsed it with domino in one synchronous call, so one page stalled the stdio server for minutes, exhausted a 4 GB heap (`<b id=N><p>x` x2500, 35 KB) or overflowed the stack (~1,150 nested elements). The bounds, each pinned by `src/tests/markdown.test.ts`: (1) domino's incremental parser runs in `PARSE_SLICE_MS` (10 ms) slices, yielding with `setImmediate`, checking the deadline and `signal` -- never `domino.createDocument` on fetched HTML; (2) a DOM budget, `MIN_NODE_BUDGET` + one node per `NODE_BUDGET_CHARS` input characters, capped at `MAX_NODE_BUDGET` (100,000 + length/8, at most 250,000), checked at EVERY parser step (one token can re-create a whole list of formatting elements): `DomWeight` reads domino's private `doc._nextnid`, and scans each newly rooted node in `doc._nodes` once for its `_attrKeys`, counting an attribute as 1/`ATTRS_PER_NODE` (1/4) of a node; and `countedTemplateDoc()` gives the parse its own inert template document whose content fragments are rooted in it, because domino never roots `<template>` content and the budget saw none of it (36 KB of `<template>` then `<b id=N><p>x` built 2.6 GB; 814 KB of `<b>` with 676 attributes then `<p>x`, whose clones copy every attribute, built 3.5 GB in 30 s). Measured on Node 22: a parsed-and-converted node costs ~1 KB of peak RSS and an attribute ~160-180 B, so one conversion stays near 250 MB (a converted 4 MiB page at ~237,000 nodes: 243 MB; 1 MiB of `<p>x`, which held ~500 MB under the old 100,000 + one-per-character, 1,000,000-cap budget, is refused at 111 MB). The 20 real pages built at most 42,440 nodes (0.05 per character) and none used more than 1/4.4 of its budget. This is why `@mixmark-io/domino` is pinned EXACTLY -- the pin tests on `_nextnid`, `_nodes`/`_attrKeys` and the counted template document fail if an upgrade moves them, and the budget would otherwise silently vanish; (2b) a page longer than `MAX_MARKDOWN_INPUT` (8 Mi UTF-16 units, above the 5 MiB default `max_bytes`) is refused before anything is built, with an error pointing to `fetch_html_to_text`: peak memory scales with the text as well as the DOM, one 100 MiB conversion took 1.5-3 GB and 8 concurrent ones OOM-crashed Node, while one conversion of the worst 8 MiB shapes measured (flat lines or paragraphs under 200 nested blockquotes, a `<pre>` under 30 nested blockquotes or 100 list items, escape-heavy text, text-heavy tables) raises peak RSS by 140-780 MB on the default heap -- mostly garbage V8 has not collected: each completes under `--max-old-space-size=256` at 270-370 MB of RSS (before the work cap and `MAX_TURNDOWN_MS` below, the blockquote shapes reached 1.2-1.4 GB); (2c) at most `MAX_CONCURRENT_CONVERSIONS` (2) conversions, holding at most `MAX_INPUT_IN_FLIGHT` (12 Mi, 1.5x the ceiling) input characters between them, run at once, and one call is always admitted when none runs -- so two pages near the ceiling never convert together: sliced parses interleave, so before the limit 8 concurrent 1 MiB calls each held a full DOM (2.7 GB peak RSS); measured on Node 22, an admitted pair of the worst shapes (6 MiB each) raises peak RSS by 650-740 MB on the default heap and completes under `--max-old-space-size=256` at 300-390 MB, and 8 concurrent calls of the worst 8 MiB shapes peak 0.9-1.15 GB of RSS on the default heap and all complete under `--max-old-space-size=384` at 380-560 MB. A call past either limit waits in a FIFO queue holding only its input, leaves it on its `signal` or its deadline, and the wait counts against its budget. A freed slot is handed over from `setImmediate`, so the loop turns between conversions, and the handoff settles a waiter whose deadline passed or whose signal fired instead of granting it (a conversion that held the loop kept the waiters' timers from firing: 16 queued calls each ran up to 3.6 s past budget); `convert()` re-checks the deadline before building the wrapped string. 8 concurrent calls now fit a 384-512 MB heap where every shape above OOMed it (peak RSS on the default heap can still read ~1.2 GB for 8 converted 4 MiB pages: uncollected garbage, not live DOM); (3) an iterative walk refuses nesting past `MAX_MARKDOWN_DEPTH` (256) BEFORE Turndown recurses, and more than `MAX_TAG_NAMES` (1,024) distinct tag names or `MAX_TAG_NAME_CHARS` (16 KiB) of them -- it reads `localName`/`prefix`, never `tagName`/`nodeName`, because domino's module-level `uppercaseCache` keeps every HTML tag name it uppercases forever (residual: a page under the limits still adds its new names, at most 16 KiB of them, for the life of the process); (4) the vendored Turndown in `src/vendor/turndown/turndown.js` with its patches: (a) node-only input, no clone, no parser `require`; (b) linear child join; (c) linear trailing-whitespace trim; (d)+(f) one post-order pass precomputes per node what upstream re-derived from `textContent` or a subtree walk at EVERY node (whitespace-only, edge whitespace runs, first/last char, void / meaningful-when-blank descendants, `<ol>` index), so each node is O(1) -- never add a per-node `textContent`, `getElementsByTagName`, `children` or subtree walk to the conversion path; (e) the deadline checked at every node visit (collapse, pre-pass, `process()`), throwing `ConversionDeadlineError`; (g) replacement work charged before it runs (deadline re-checked every 64 Ki characters) and a per-parent output cap, `OUTPUT_FACTOR` x page + `OUTPUT_SLACK` (4x + 1 MiB; the largest intermediate string on the 20 real pages was 0.77x), throwing `ConversionLimitError` before the join -- this is what stops nested `<blockquote>`/`<li>` rules from re-prefixing an O(depth x content) string -- and a whole-conversion work cap, `maxWork` = `WORK_FACTOR` x page + `WORK_SLACK` (64x + 16 Mi; the 20 real pages, alone or repeated to 4-8 MiB, charged at most 8.4x), throwing `ConversionLimitError` with `kind: "work"` before the work runs: 200 nested blockquotes around flat `<br>` lines or `<p>`s re-prefix every line at each level without any one parent passing the output cap (1,000-1,800x the page in work; 1 MiB held the loop 16.6 s, 3 MiB 37 s; now refused in 0.2-0.5 s, 8 MiB in ~1.5 s). The cap is a known divergence from 0.8.3, which had none: a page that re-prefixes one long block at every level is refused (a 1.2 MB `<pre>` of 1-character lines inside 2 nested list items or 4 `<blockquote>`s; of 40-character lines, 40 list items or 80 `<blockquote>`s), while the 20 real pages peak at 0.77x, ~5x under it; (h) `collapseWhitespace()` runs with domino's `doc.modclock` at 0 so each removal does not walk all ancestors; (i) the inline-code rule's extra-space test and delimiter are single passes (upstream's `/^`|^ .*?[^ ].* $|`$/` backtracked quadratically: 100 KB took 17.6 s); (j) no single string operation runs on more than 64 Ki characters between two deadline checks, however long one text node, attribute or rule content is -- the escapes (text, image alt, link href/src/title), `cleanAttribute()`, the whitespace collapse, `trim()`, and the blockquote, list-item and inline-code rewrites go through `boundedReplace()`, cut only where no match can straddle; each chunk's result is flattened at once (V8 returns a global replace as a rope of one node per match, ~30x the heap until joined, and the GC pauses with it); run scans check every 64 Ki; a check brackets each whole-string copy. Strings up to 64 Ki run upstream's expression unchanged and `chunkSize` lets tests force the chunked paths: never add an unchunked regex, `trim()` or scan over a whole text node, attribute or content to the conversion path; (k) nothing is converted only to be discarded and no nesting level keeps its own copy of the text: a rule marked `ignoresContent` (the default blank and keep rules, `remove()`, and `makeTurndown()`'s two removal rules) gets `''` without `process()` or `trimWs()` over its subtree, and the cached whitespace runs from (f) -- ropes shared with every ancestor's, which V8 flattens IN PLACE on the first `substring()` or character read -- are never read directly: `flankingWhitespace()` takes precomputed `_tdLeadRest`/`_tdTrailRest` ropes instead of `substring()`, and `emitReplacement()` copies a replacement that would be a cached run itself. Before (k), 2.5 MB of `<span>`+NBSP nested 250 deep took 9.7 s and 678 MB, 20 MB of it (or of empty `<i>`s, or of space-flanked runs in `<pre>`) OOM-killed a 4 GB heap, and the tree retained ~100 bytes per input character at 100 deep; after, 0.4 s and 131 MB peak RSS at 20 MB, <=0.2 bytes per character retained, the 20 MB shapes complete inside a 200 MB (10x) heap, and at 100 MB none OOMs (peak RSS up to ~3 GB on the default heap, mostly uncollected garbage; the deep shapes finish or reach a 120 s budget inside a 1 GB heap). Never call `substring()`, `charCodeAt()` or a regex on a cached `_td*` run, and mark a new rule `ignoresContent` when its replacement never reads `content`. Residual, bounded only by the deadline: an element that is not blank re-trims the whitespace of its whole subtree at every level (an empty `<i>` or `<pre>` runs nested 250 deep), O(depth x text) in time but not in retained heap -- ~30 s at 20 MB on a loaded machine, so the default 10 s budget stops it. Never import the npm `turndown` package (the vendor-guard test fails), never let another module import domino or the vendored file, and keep `htmlToMarkdown()` non-throwing: tools turn its `{ error }` into `formatError`. The conversion gets its own `timeout_ms` budget, counted from the `htmlToMarkdown()` call, so a wait for a conversion slot spends it. Re-sync upstream Turndown fixes by hand, and diff the output against the previous version on a set of real pages before landing a change here (output was byte-identical to npm turndown 7.2.4 on 20 real pages when this landed). The oam lane (#21) covers a hostile page end to end. The Turndown step after parsing is still synchronous: it is bounded by the deadline and the two caps, not by yielding, so it holds the event loop -- every other call and every cancellation -- until it finishes or stops. So its deadline is the budget's or `MAX_TURNDOWN_MS` (4 s) from the step's start, whichever is sooner, and a stop at the step cap gets its own error pointing to `fetch_html_to_text`: with `timeout_ms` up to 120 s, the budget alone let one step hold the loop for the whole of it (a queued call with a 2 s budget answered at 32 s, a cancel at 3 s landed at 41 s). The 4 s is 3x the slowest real page measured (the 20 pages, and each repeated to 4-8 MiB: at most 1.2 s of loop held, parse slices and tree walk included; the Turndown step alone at most 0.9 s); the worst hostile shapes found now hold it at most ~2.2 s (a `<pre>` of short lines under 20 nested `<blockquote>`s, 6 MiB). Never derive the step cap from the budget. Only one step runs per event-loop turn: every conversion waits at a module-level step gate (`acquireStep()`/`releaseStep()`, FIFO, the same signal and deadline handling as the slot queue) after its parse, and each grant comes from a `setImmediate` scheduled after the previous step ended -- even with no step running, so a parse that finished in its first slice never runs its step in the caller's microtask. Without it, two admitted parses that finished in the same check phase ran their steps back to back and the stall was the sum (two of the 6 MiB pages above: 3.2-4.5 s; a 100 ms abort fired at 4.1 s, after the call it was meant to cancel had converted); now ~2.2 s, and the cancel lands as soon as the step ahead ends. Never grant the next step from inside `releaseStep()`, and re-check the signal and deadline after the grant. `htmlToMarkdown()`'s `turndownMs` option can only lower it (tests). How far a stop can overrun the deadline is the longest interval between two checks: at most ~35 ms on 31 hostile 5 MiB shapes, ~250 ms in the Turndown step at the 100 MiB `max_bytes` ceiling (before (j): 1.36 s at 5 MiB). Residual, in the parse: domino's tokenizer appends text one character at a time on runs of `\r\n`, entities or stray `<` (a rope that GC and the first read pay for) and builds a comment in one `buf2str`, so one parse slice still held the loop for up to ~1.2 s on 100 MiB of `\r\n` (~0.3 s at 20 MiB, <=35 ms at 5 MiB). Keep output byte-identical when touching the patches: besides the 20 pages, a differential fuzz against the previous vendored file (whitespace-heavy inline/`<pre>` markup) is how (f) was checked; (i), (j) and (k) were checked the same way with `chunkSize` forced to 1-9, plus a string-level differential of each helper against upstream's own expression (exhaustive to length 6, the code-span test to length 8).

## Convention quick-list

- Use npm, keep the lockfile committed.
- Run `npm run lint:fix` + `npm run typecheck` + `npm test` before every commit. Nothing runs checks for you -- no GitHub Actions, no git hooks -- so this local pass and `release.sh` steps 1-2 are the only checks. (A PR is still required to land on `main`; see below. It gates the merge, not the code.)
- Record user-facing changes under `## [Unreleased]` in `CHANGELOG.md` as you land them; `release.sh` promotes that heading to the release version.
- zod schemas describe tool input; the exported TypeScript type is derived from the zod shape, not hand-written.
- Tool callbacks always return a `formatX()` result — never throw. Upstream errors get caught and returned as `formatError(...)`.

## Landing changes: `main` requires a pull request

`main` and the release tags are guarded by three repository **rulesets**. They are not classic branch protection, so `gh api repos/YawLabs/fetch-mcp/branches/main/protection` answers 404 "Branch not protected" -- that answer is WRONG for this repo. Read `gh api repos/YawLabs/fetch-mcp/rules/branches/main` instead.

| Ruleset | Target | Rules | Who can bypass |
|---|---|---|---|
| Protect default branch | `main` | pull request required; 0 approvals; merge, squash or rebase | org admins |
| Protect release tags | `refs/tags/v*` | creation, deletion, non-fast-forward | org admins |
| Block force-push and deletion | `main` | deletion, non-fast-forward | nobody |

Jeff is an org admin, so a direct `git push origin main` from his account **succeeds**. The only sign is a line in the push output: `remote: Bypassed rule violations for refs/heads/main: - Changes must be made through a pull request.` That is a bypass of his protection, which his global rules forbid without asking first. On 2026-09-21 two non-release commits (`12363b4`, `ac4cccf`) went in that way before anyone noticed.

- **Every non-release change:** branch -> commit -> push the branch (with `GIT_SSH_COMMAND`) -> `gh pr create` -> `gh pr merge <N> --squash`. Zero approvals are required, so the merge needs no `--admin`.
- **The one sanctioned direct push is `release.sh` step 4:** the `vX.Y.Z` commit and its annotated tag, both through the org-admin bypass (creating a `v*` tag is admin-only). So land the changes by PR first, `git pull` on `main`, then run `./release.sh` from the clean, up-to-date `main`.
- **After any push, read the remote output.** "Bypassed rule violations" on anything other than a `release.sh` push means stop and tell Jeff.
- Force-push and deletion on `main` are blocked for everyone, admins included. There is no bypass to reach for.

## Release

**`./release.sh X.Y.Z` from a clean `main` on the workstation is the whole pipeline**, once the changes have landed by PR (above). The repo has no GitHub Actions workflows and Actions is disabled on it (workflows removed 2026-07-21), so nothing fires on tag push and nothing re-checks the tree after you. Don't hand-roll `npm version` + tag + push: that tags a version nobody publishes.

Before step 1 it runs `scripts/check-oam-floor.mjs`: it fails when `OAM_MIN` is behind the latest oam release (`FETCH_MCP_ALLOW_STALE_OAM=1` releases on the old floor deliberately) and, like `src/tests/oam-floor.test.ts` on every `npm test`, when any floor claim in the launcher, README, this file or the launcher test disagrees with `OAM_MIN`.

The script runs eight steps. Each is idempotent, so after an interruption re-run with the same version to resume:

1. Lint + typecheck -- the only lint gate this repo has.
2. Build + test. Then the real-oam lane (Launch-critical #21) on the oam `scripts/find-test-oam.mjs` picks (warns when there is none), and `scripts/check-compliance.mjs`: `@yawlabs/mcp-compliance` against the built launcher, failing below grade A or on a failed required test, warning when it produced no grade.
3. Bump `package.json` / `package-lock.json`, sync `server.json`, and promote `## [Unreleased]` in `CHANGELOG.md` to the version. Aborts if the release would ship with unpromoted `[Unreleased]` content.
4. Commit `vX.Y.Z`, create an annotated tag, `git push origin main --follow-tags`. This direct push, and the `v*` tag creation, go through the org-admin ruleset bypass; the output shows "Bypassed rule violations" for both refs. It is the only sanctioned bypass.
5. `npm publish`, with EOTP retry.
6. GitHub release. Its notes are the CHANGELOG section for the version (passed by file), so the `[Unreleased]` block is what people read on the release page.
7. Smoke test (below), then MCP Registry publish via `mcp-publisher` (token: `MCP_REGISTRY_TOKEN`, else `gh auth token`).
8. Verify: the npm version, `package.json` and the git tag. Mismatches only warn.

**Auth:** an npm automation token in `~/.npmrc`; pre-flight aborts if `npm whoami` fails. Never `npm login --auth-type=web` -- it overwrites the automation token with a 2FA-bound session and the next publish EOTPs. The tag lands in step 4, before publish, so a tag is not proof of registry presence; check `curl -s -o /dev/null -w '%{http_code}' https://registry.npmjs.org/@yawlabs%2Ffetch-mcp/X.Y.Z` (200 = published; `npm view` reads the packument, which Cloudflare caches for up to 5 min after a publish).

`release.sh` still carries a `CI=true` mode and a hand-off-to-`release.yml` branch from the Actions era. Both stay dormant while no workflow exists.

**Smoke test:** step 7 installs the just-published version with `npx` from a temp dir (retrying 60 times 10 s apart -- ~10 min of sleeps plus each npx run -- while the registry propagates), runs it with `--version`, and fails the release unless the output equals the version. It catches packaging regressions: a missing bin shebang, a bad `"files"` entry, broken tsup output. It depends on the argument handling in `src/index.ts` (Launch-critical #9).
